Project Methodology

1. Problem Formulation

The scheduling task is defined as a Constraint Satisfaction Problem (CSP). We map all academic rules (teacher availability, room capacity, session quotas) into a set of linear equations and boolean indicators.

2. Solver Engineering

Using Google OR-Tools CP-SAT, we implement a lazy-clause generation approach. This allows the system to prune trillions of invalid combinations in milliseconds, focusing only on feasible regions of the search space.

3. Optimization Strategy

The system uses a Weighted Objective Function to balance competing soft constraints. This ensures that while all hard rules are met, the resulting timetable is also "fair" and efficient for everyone involved.

Constraint Engine: CP-SAT

The core intelligence resides in engine.py, which translates academic requirements into mathematical constraints.

Hard Constraints

  • No Teacher Overlaps
  • No Room Conflicts
  • Student Batch Sync
  • Temporal Continuity (Labs)
  • Room Capacity Limits
  • Teacher Availability

Optimization Goals (Soft)

  • Parallel Lab Sessions
  • Minimized Student Gaps
  • Teacher Daily Load Balancing
  • Preferred Morning Slots

Low-Level Implementation

Variable Modeling

The solver uses a 5-dimensional boolean decision matrix:

x[course, batch, teacher, room, slot] ∈ {0, 1}

This allows for granular control over every possible assignment combination, though it results in a sparse matrix with thousands of variables.

Temporal neighbor logic

To enforce 2-hour lab blocks, the solver implements a "neighbor requirement" logic:

# If a lab is active at slot S, it MUST have a neighbor at S-1 or S+1 model.Add(slot_indicator[S] <= slot_indicator[S-1] + slot_indicator[S+1])

This is combined with a temporal gap check to ensure the slots are physically contiguous (e.g., 10:00 ends exactly when 11:00 starts).

Worker Pipeline Internals

  1. Data Wrapping: SQLAlchemy models are hydrated and indexed into O(1) lookup dictionaries.
  2. Unit Allocation: Courses are decomposed into "Units" (e.g., a Lab shared by 3 batches becomes 3 independent solver units).
  3. Conflict Graph: Batch-group parent mappings are used to prevent overlaps between a student's theory and lab sessions.
  4. Persistence: Transactional database commit ensures either the entire timetable is saved or nothing is.

Parallelism Logic (Soft Constraint)

Synchronization of labs across batches is achieved using Boolean indicators:

# is_synced is True ONLY IF all batches of a group are scheduled in the same slot model.Add(sum(batch_activity) == num_batches).OnlyEnforceIf(is_synced) # A penalty is applied to the objective function if a lab is active but not synced penalties.append(partial_sync * 500)
